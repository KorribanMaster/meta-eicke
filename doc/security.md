# Security

Everything security in one place: production hardening, the verified-boot
chains (including the x86 UEFI Secure Boot setup), and the encrypted-`/data`
status. Prod = `eicke-image-prod` + `eicke-image-netboot-prod`, both via
`recipes-core/images/eicke-prod-hardening.inc`.

## Overview

| Measure | Where | Scope |
|---|---|---|
| Real credentials, dev-laxness removal | `eicke-prod-hardening.inc` | prod |
| Key-only SSH | `eicke-prod-hardening.inc` | prod |
| Verified boot mandatory (build refuses without it) | `eicke-prod-hardening.inc` | prod |
| Hardening sysctls | `eicke-sysctl-hardening` | prod |
| Default-deny inbound firewall | `eicke-firewall` | prod |
| Read-only rootfs, `/etc` overlay, minimal modules | `eicke-image-prod.bb` | prod (per-image) |
| Kernel hardening (module signing, lockdown, …) | `recipes-kernel/linux/linux-yocto/hardening*.cfg` | **all images** (shared kernel) |
| SWUpdate hardware-compatibility gating | swupdate defconfig + `eicke-hwrevision` + all sw-descriptions | **all images** (shared binary) |
| Signed `.swu` bundles (RSA-PSS, compiled-in) | `swupdate-signing.inc` | all images |
| Compiler hardening (PIE, fortify, stack protector) | oe-core `defaultsetup.conf` → `security_flags.inc` | all images |
| Encrypted `/data` (LUKS2 + TPM2) | `eicke-initramfs*` | **WIP — wired, not active** (see below) |

## Production hardening

### Credentials and SSH

The dev laxness (`allow-empty-password empty-root-password allow-root-login`
from `local.conf`) is removed; real SHA-512 hashes for `root` and `eicke`
come from the **gitignored** `eicke-image-prod-creds.inc` (generated with
random passwords by `eicke-init-build-env`; the build fails loudly if it is
missing).

SSH is key-only: ed25519 keys (`EICKE_SSH_PUBKEY`, overridable from
local.conf) in root-owned `/etc/ssh/authorized_keys.d/<user>`, and
`/etc/ssh/sshd_config.d/99-eicke-prod.conf` sets `PasswordAuthentication no`,
`KbdInteractiveAuthentication no`, `PermitRootLogin prohibit-password`.
Root stays key-reachable because the image ships no sudo and `eicke`'s shell
is `/bin/sh` — root-by-key is the only remote admin path. Local console
(getty) password login is unaffected.

    sshd -T | grep -E 'passwordauthentication|kbdinteractiveauthentication|permitrootlogin'
    # -> no / no / prohibit-password

### Verified boot is mandatory

`eicke-prod-hardening.inc` skips the recipe when the `eicke-verified-boot`
feature is off (`Nothing PROVIDES 'eicke-image-prod' … requires
EICKE_VERIFIED_BOOT=1`). qemu bring-up escape hatch:
`EICKE_ALLOW_UNVERIFIED_PROD = "1"` (warns, never releasable).
`eicke-image-netboot-prod` keeps its own non-overridable skip — an unsigned
netboot chain is meaningless.

### Kernel hardening (all machines, all images)

Fragments in `recipes-kernel/linux/linux-yocto/` (per-option rationale in
the files): `hardening.cfg` — module signing incl. `MODULE_SIG_FORCE`,
lockdown LSM forced to *integrity* mode, Yama, `FORTIFY_SOURCE`,
`HARDENED_USERCOPY`, `SLAB_FREELIST_RANDOM/HARDENED`,
`INIT_ON_ALLOC_DEFAULT_ON`, `BUG_ON_DATA_CORRUPTION`, `DEVMEM=n`,
`PROC_KCORE=n`; `hardening-x86.cfg` — `LEGACY_VSYSCALL_NONE`.

One kernel for dev and prod is deliberate (single tested kernel, dev/prod
parity): lockdown *integrity* — not *confidentiality* — keeps tracing/perf/
debugfs usable on dev, and every loadable module comes from this same build,
signed at `modules_install`, so `MODULE_SIG_FORCE` costs dev nothing.

Merge-order caveat: user `SRC_URI` fragments are merged **before**
kernel-cache feature fragments, so a `=y` here silently loses to a feature's
`=m` (that is why the firewall's nft modules ship as signed
`kernel-module-*` RDEPENDS of `eicke-firewall` instead of a fragment). After
fragment changes run `bitbake linux-yocto -c kernel_configcheck` and grep
the final `.config`.

    # on target:
    cat /sys/kernel/security/lockdown   # -> none [integrity] confidentiality
    ls /dev/mem /proc/kcore             # -> No such file or directory
    insmod unsigned-hello.ko            # -> Key was rejected by service

Known caveat: the module-signing key is autogenerated per kernel build; an
sstate-restored out-of-tree module (`zynq-pcie-rproc`) signed against a
previous build would be rejected at load. If observed, point
`CONFIG_MODULE_SIG_KEY` at a stable key in `EICKE_KEYS_DIR`.

### Sysctls

`eicke-sysctl-hardening` → `/etc/sysctl.d/99-eicke-hardening.conf`:
kptr/dmesg/perf restrictions, `yama.ptrace_scope=1`, unprivileged BPF pinned
off, no unprivileged user namespaces, SYN cookies, strict rp_filter, no
redirects/source-route, protected symlinks/hardlinks/FIFOs. Per-key
rationale in the file.

    sysctl kernel.yama.ptrace_scope kernel.dmesg_restrict kernel.kptr_restrict kernel.unprivileged_bpf_disabled
    # -> 1 / 1 / 2 / 1

### Firewall

`eicke-firewall`: static nftables ruleset (`/etc/nftables.conf`) loaded by a
oneshot unit before `network-pre.target` (no up-but-unfiltered window).
Inbound default-**drop**; open: lo, established/related, ICMP/ICMPv6, tcp 22
(SSH), tcp 8080 (SWUpdate web UI — kept because signed-bundle verification,
not reachability, is the update trust boundary). Side effect: resolved's
LLMNR/mDNS are unreachable from outside.

    systemctl status eicke-firewall && nft list ruleset

### SWUpdate: signatures + hardware gating (all images)

Every `.swu` must carry a valid RSA-PSS signature over its sw-description
(`CONFIG_SIGNED_IMAGES=y` — compiled in, so every image verifies; key pair:
`EICKE_KEYS_DIR/swupdate-priv.pem` ↔ `/etc/swupdate/public.pem` via
`swupdate-public-key`).

`CONFIG_HW_COMPATIBILITY=y` + `/etc/hwrevision` (`eicke-hwrevision`,
revision = bitbake `MACHINE`) + `hardware-compatibility: [ "@@MACHINE@@" ]`
in every sw-description: a bundle built for another machine is refused
before anything is written. Migration semantics:
[images/eicke-update-image.md](images/eicke-update-image.md).

    cat /etc/hwrevision                       # -> eicke qemux86-64
    swupdate -H eicke:bogus -i <bundle>.swu   # -> refused (HW compatibility)

End-to-end check of all of the above on qemux86-64:
`pytest -m secureboot scripts/test` (`test_hardening_x86.py`: boots the prod
wic via runqemu, drives it over SSH with the test key; see
[testing](testing.md)).

## Verified boot

Scope: the bootloader is the trust anchor; the pre-bootloader chain
(BootROM/SPL/fuses, UEFI db enrollment) is hardware-specific and out of
scope.

### The switch

    EICKE_VERIFIED_BOOT = "1"

sets the `eicke-verified-boot` distro feature (everything gates on it) and,
on x86, meta-secure-core's `efi-secure-boot`. x86 additionally needs (see
`local.conf.sample`; `BOOT_GPG_*` values come from your key store's
`sb-user/keys.conf`):

    UEFI_SELOADER = "1"
    GRUB_SIGN_VERIFY = "0"
    BOOT_GPG_NAME = "BOOT-SecureCore"
    BOOT_GPG_PASSPHRASE = "<from sb-user/keys.conf>"

Key store: one generator (`scripts/eicke-gen-keys.sh`, `--secure-boot` for
the x86 store), one location — host `~/yocto` mounted at `/yocto` in the
build container (`EICKE_KEYS_DIR = /yocto/keys`; `dock.sh` mounts only the
workspace, so add `-v $HOME/yocto:/yocto` — the same mount provides
downloads/sstate per `site.conf`). Key vocabulary and store-layout defaults
(`MASTER_KEYS_DIR` etc.) live in `conf/distro/eicke.conf` — local.conf only
needs the knobs above. All required layers are in the template
`bblayers.conf`.

`efi-secure-boot` is **distro-wide** (patches grub, signs the kernel for
every image), but only the prod images are wired for the signed-ESP boot
flow (`eicke-ab-prod.wks.in`); base/dev keep the unsigned `bootimg-efi` wks.

### The three chains

| | **GRUB** (x86 disk, `eicke-image-prod`) | **iPXE** (x86 netboot, `eicke-image-netboot-prod`) | **U-Boot** (ARM, `eicke-image-prod` on qemuarm-uboot) |
|---|---|---|---|
| Trust root | UEFI db → shim/MOK | UEFI db **directly** (no shim) | RSA pubkey in U-Boot control DTB |
| Chain | db → shim → SELoader → grub → signed bzImage + `.p7b` | db → signed `ipxe.efi` → HTTP → signed UKI (firmware `LoadImage` verifies) | (verified U-Boot) → signed kernel FIT via `bootm` |
| Boot logic integrity | signed `boot-menu.inc` (grub verifies) | firmware BootNext/BootOrder entries | compiled-in `bootcmd` (part of the U-Boot binary) |
| A/B unit | rootfs slots + `rootdev/ustate/bootcount` | iPXE-binary A/B via UEFI BootNext; OS is stateless RAM-boot | rootfs slots + `uboot.env` (same contract) |
| Confirm/rollback | `eicke-bootconfirm` clears `ustate` | `eicke-ipxeconfirm` promotes BootOrder | `eicke-bootconfirm` (shared script/lib) |
| Signing key | `sb-user/uefi_sb_keys` DB | **same** DB key | standalone `eicke-fit` RSA |

Who signs what: `.swu` → `swupdate-priv.pem` (RSA-PSS); x86
kernel/grub/shim/UKI/iPXE → `sb-user/uefi_sb_keys/DB.{key,crt}`
(PE/Authenticode + PKCS7); ARM kernel FIT → `eicke-fit.{key,crt}` (FIT
signature node).

Three trust models on purpose — they follow the hardware: GRUB bridges to
the UEFI db via shim/SELoader and verifies detached signatures as it walks
the flow; iPXE defers verification to the firmware's `LoadImage`; U-Boot
verifies one signed container (the FIT) with its own embedded key.
Everything around them is shared: one switch, one key store, one A/B state
contract (`rootdev`/`ustate`/`bootcount` treated as untrusted data — see
[images/eicke-update-image.md](images/eicke-update-image.md)), one confirm
lifecycle (`eicke-confirm-lib.sh`), one update mechanism, and 1:1-mirrored
GRUB/U-Boot boot logic.

### x86: how the GRUB chain is assembled

Built with [meta-secure-core](https://github.com/Wind-River/meta-secure-core)
(wrynose): SELoader publishes the MOK2/PKCS7 verify protocol grub uses to
authenticate `grub.cfg`, `boot-menu.inc` and the kernel. `SIGNING_MODEL =
"user"` (distro default) uses our store and auto-blacklists the layer's
sample keys in DBX — an image signed with our keys is rejected by a
sample-key varstore and vice-versa (verified). meta-eicke's pieces:
`recipes-bsp/grub/grub-efi_%.bbappend` + `files/boot-menu.inc` (our A/B
logic, shadowed so it gets signed), `packagegroup-efi-secure-boot` +
`eicke-ab-prod.wks.in` in the prod image, and the standalone `grubenv` seed
gated off under `efi-secure-boot` (grub-efi ships grubenv itself).

QEMU verification (previously verified: SB on in the guest; foreign-db
varstore → firmware `Access Denied`; tampered kernel → grub `failed to
verify kernel`):

1. `bitbake ovmf` → `ovmf.secboot.code.qcow2`;
2. pre-enroll PK/KEK/db into a varstore (`virt-fw-vars --no-microsoft
   --secure-boot`) from our `sb-user/uefi_sb_keys/*.crt`;
3. boot with both pflash drives + the prod wic.

### x86 netboot: the iPXE chain (no shim)

`ipxe_git.bb` signs `ipxe.efi` straight into **db** (the UEFI BootNext A/B
entries point directly at `ipxe-a.efi`/`ipxe-b.efi`; shim's fixed next-stage
name doesn't fit), and `eicke-netboot-prod-uki.bb` builds a db-signed UKI
(stub + bzImage + the image's cpio + fixed cmdline, inner kernel also
signed) that iPXE chains over HTTP and the firmware's `LoadImage` verifies.
QEMU flow scripted in `scripts/eicke-netboot-prod-sim.sh`. See
[images/eicke-image-netboot-prod.md](images/eicke-image-netboot-prod.md).

### ARM: what is still missing

**Runtime FIT enforcement under QEMU.** `uboot-sign` embeds the pubkey into
the *built* `u-boot.dtb`, but qemu-virt hands U-Boot its control DTB at
runtime (`OF_BOARD`), so the FIT signature is build-verified, not
boot-enforced (`conf/machine/include/eicke-verified-boot.inc` documents
this; `UBOOT_SIGN_ENABLE` stays off). Path if needed under qemu: dump the
qemu DTB, insert the `/signature` node (`mkimage -K`), feed it back via
`-dtb`, mark the FIT conf key `required`, drop `CONFIG_LEGACY_IMAGE_FORMAT`.
On real hardware the key lives in a fused/verified U-Boot's DTB and the gap
disappears — emulator plumbing, same class as the swtpm limitation below.

## Encrypted /data (WIP — wired, not active)

**Design** (agreed): encrypt **`/data` only** (LUKS2); the rootfs stays
plaintext read-only (integrity comes from verified boot); the persistent
`/etc` overlay's upper dir lives on the encrypted `/data`. A **signed
initramfs** (`eicke-initramfs.bb` + `eicke-initramfs-init.bb`) runs before
`switch_root`: first boot it `luksFormat`s `/data` and enrolls the key into
the TPM sealed to **PCR 7** (Secure Boot state) via `systemd-cryptenroll`;
every boot it unlocks via the systemd-tpm2 token, lays the `/etc` overlay,
and `switch_root`s — replacing the `overlayfs-etc` preinit.

**Status:** the whole pipeline is implemented and QEMU-verified up to the
final TPM operation — the signed separate initrd is SELoader-verified and
loaded, `/init` runs, finds rootfs + data, and talks to the TPM. The single
blocker is the **swtpm emulator**: systemd ≥256 requires an AES-128-CFB
encrypted TPM session and the swtpm/OVMF tpm-crb combination fails it
(kernel `tpm0: TPM error (256)` = `TPM_RC_INITIALIZE` at probe; profile /
`swtpm_setup` / startup-flag variations didn't help). Real hardware TPMs
support this — it is an emulator/firmware-init limitation, not product code.
Prod therefore currently ships the `overlayfs-etc` preinit with a
**plaintext** `/data`; the crypto tools (`cryptsetup tpm2-tools
cryptfs-tpm2`) are installed but unused.

**Next steps** (pick one): verify on real hardware (recommended); or fix the
qemu TPM init (`tpm-tis` instead of `tpm-crb`, confirm OVMF runs Tcg2Dxe /
`TPM2_Startup`, or an early `tpm2_startup -c` in `/init`).

**To re-activate** in `eicke-image-prod.bb`: drop `overlayfs-etc` (inherit,
IMAGE_FEATURES, `OVERLAYFS_ETC_*`, the fstab /data-line strip); add
`kernel-initramfs` + a postprocess that derefs `/boot/initrd{,.p7b}` to real
files; `INITRAMFS_IMAGE = "eicke-initramfs"`, `INITRAMFS_IMAGE_BUNDLE = "0"`
in local.conf; `initrd /boot/initrd` after the `linux` line in
`boot-menu.inc`. (`/init` force-logs to `/dev/ttyS0` — make that conditional
first. Note: `INITRAMFS_IMAGE_BUNDLE = "1"` does NOT work — the bundled
initramfs isn't part of what meta-efi-secure-boot signs; the separate signed
initrd path is the verified one.)
