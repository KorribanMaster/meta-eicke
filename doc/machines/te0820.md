# te0820

**Trenz TE0820-02-02CG-1E** (PCB REV02): Zynq UltraScale+ XCZU2CG (2× Cortex-A53,
2× Cortex-R5F), 1 GiB DDR4, 4 GB eMMC, 2× 32 MiB QSPI flash (dual parallel), on a
**TE0703** carrier. The board runs the eicke A/B image from a **microSD card**. Only
the processing system (PS) is used: the programmable logic (PL) is not loaded at
boot.

## Where the BSP comes from

No meta-xilinx and no Xilinx tools in the build: everything comes from oe-core,
meta-arm and the board files in meta-eicke.

| Piece | Source |
|---|---|
| Machine conf | `conf/machine/te0820.conf` |
| Boot ROM payload (replaces the Xilinx FSBL) | U-Boot SPL `boot.bin`, `xilinx_zynqmp_virt_defconfig` + `recipes-bsp/u-boot/files/te0820/` |
| DDR, clocks, MIO | `psu_init_gpl.c/h` from the Trenz reference design, built into SPL |
| PMU firmware | `pmufw.elf`, 2025.2, built from the Trenz reference design's XSA, packed into `boot.bin` |
| PM configuration object | `pm_cfg_obj.bin`, loaded into the PMU firmware by SPL |
| TF-A | meta-arm `trusted-firmware-a`, `PLAT=zynqmp`, `bl31` in `u-boot.itb` |
| U-Boot | oe-core `u-boot` 2026.01, `u-boot-<hash>.itb` (FIT: TF-A, U-Boot, DTB) |
| Kernel | `linux-yocto` 6.18, kernel-cache BSP `amd-zynqmp` (`KMACHINE`) + `te0820.cfg` |
| Device tree | `files/dts/zynqmp-te0820.dts`, one file for U-Boot and Linux |

### The Trenz files

Trenz dropped REV02 from its reference design after 2020.2. The files come from the
current one, `TE0820-te0820-rd-vivado_2024.2-build_1_20250214171345.zip`
(sha256 `6da0f8fe…f66a`), `2cg_1e_2gb` prebuilt (REV03+, 2 GiB):

| File | Taken from |
|---|---|
| `psu_init_gpl.c/h` | `prebuilt/hardware/2cg_1e_2gb/te0820-rd_2cg_1e_2gb.xsa` (a zip) |
| `pmufw.elf` | built from that XSA with Vitis 2025.2 (see below), not Trenz's prebuilt |
| `pm_cfg_obj.bin` | symbol `XPm_ConfigObject` (1816 bytes) in `prebuilt/software/2cg_1e_2gb/fsbl.elf` |

**Why the PMU firmware is 2025.2.** Since TF-A 2.14 (meta-arm's version), BL31
sets bit 24 of the IPI command header on every call from a non-secure caller
(U-Boot, Linux). PMU firmware up to 2025.1, including Trenz's 2024.2
prebuilt, dispatches on the whole header word, so it sees API `0x01000013`
instead of `PM_MMIO_READ` and fails the call: U-Boot then reads a UART clock
of 0, programs a zero baud generator and hangs silently after the TF-A
banner. 2025.2 masks the API ID (`pload[0] & 0xFF`).

It is built with the error manager (`ENABLE_EM`), for the watchdog (see
[Watchdog](#watchdog)). Rebuild it (`pmufw.elf`, sha256 `caf30d49…c2f2`) with
`xsct` and the MicroBlaze toolchain from Vitis 2025.2:

```sh
xsct -eval 'hsi open_hw_design te0820-rd_2cg_1e_2gb.xsa;
  hsi generate_app -hw [hsi current_hw_design] -os standalone -proc psu_pmu_0
  -app zynqmp_pmufw -compile -sw pmufw -dir pmufw-build'
cd pmufw-build && make clean && PATH=$VITIS/gnu/microblaze/lin/bin:$PATH \
    make CFLAGS=-DENABLE_EM_VAL=1U
# -> pmufw-build/executable.elf
```

**Why the 2 GiB PS init works for REV02.** The zip's board files still have the
REV02 preset (`board_files/TE0820_2CG_1E/1.0/preset.xml`). It differs from the
REV03 one (`2.0`) only in the DDR: 4 Gbit ×16 parts with 15 row address bits
instead of 8 Gbit ×16 (`K4A8G165WB`) with 16. MIO, clocks and peripherals are
identical. In the 2 GiB `psu_init`, row bit 15 is the topmost address bit
(`ADDRMAP6.addrmap_row_b15`), so the lower 1 GiB never uses it, and the refresh
timing of the 8 Gbit parts (tRFC 350 ns) is longer than the 4 Gbit parts need
(260 ns). The device tree declares 1 GiB. If the DDR misbehaves, regenerate
`psu_init_gpl.c` in Vivado from the `1.0` preset.

**PM configuration object.** It is the default one, with three masters: the APU
(IPI channel 0, mask `0x1`), RPU0 (channel 1, `0x100`) and RPU1 (channel 2,
`0x200`). The APU may wake and suspend both RPUs and has access to all four TCM
banks, which is what Linux's `xlnx_r5_remoteproc` needs.

**Not used from the Trenz FSBL.** It programs the Si5338 clock generator over
I2C0 and pulses the Ethernet PHY reset (MIO 24) and the USB PHY reset (MIO 25).
The Si5338 only clocks the GT transceivers and the PL; the PS uses neither (the
`psu_serdes_init_data()` of this design is empty). The two resets are in the
device tree, so the Linux drivers pulse them.

### Hardware described

From the REV02 board preset and the Trenz device tree:

| MIO | Function | Device tree |
|---|---|---|
| 13–22, 23 | SD0, eMMC 8 bit, 1.8 V, reset | `&sdhci0`, `mmc1` |
| 24 | Ethernet PHY reset (active low) | `reset-gpios` of `ethernet-phy@1` |
| 25 | USB3320 reset (active low) | `reset-gpios` of `&usb0` |
| 30–31 | UART0, console | `&uart0`, `ttyPS0` |
| 38–39 | I2C0: Si5338 (`0x70`), MAC EEPROM 24AA025 (`0x50`) | `&i2c0`, `eeprom@50` |
| 46–51 | SD1, microSD 4 bit, 3.3 V, no card detect | `&sdhci1`, `mmc0` |
| 52–63 | USB0 ULPI, USB 2.0 host | `&usb0`, `&dwc3_0` |
| 64–77 | GEM3 RGMII + MDIO, Marvell 88E151x at address 1 | `&gem3` |

In Linux the microSD is aliased to `mmc0`, so the slot devices are
`mmcblk0p2/p3` as on ax7015b. U-Boot keeps the hardware order instead
(`zynqmp-te0820-u-boot.dtsi`: `mmc0` = eMMC, `mmc1` = microSD), because SPL
boots the SD1 boot mode from mmc device 1; the env and the bootcmd use
`mmc 1`.
The MAC address comes from the EEPROM (offset `0xfa`) through an nvmem cell.

The PS system monitor (`ams_ps`) is enabled: Linux reads the die
temperatures (thermal zones `apu-thermal`, `rpu-thermal`, hwmon `ams`). The
PL system monitor needs a configured PL, so it and its thermal zone are
left out.

Only two Cortex-A53 cores: the dts deletes `cpu2`/`cpu3` of `zynqmp.dtsi` and
what refers to them (PMU interrupts, APU cooling map, debug nodes).

Not described: the QSPI flash (dual parallel, which mainline `spi-zynqmp-gqspi`
does not support), I2C1 (EMIO, so it needs a bitstream; the module CPLD is on
it) and anything in the PL.

## Boot flow and A/B

1. The boot ROM loads `boot.bin` from the first FAT partition of the microSD
   (boot mode SD1, `0x5`): U-Boot SPL and the PMU firmware, which the boot ROM
   starts on the PMU.
2. SPL runs `psu_init` (DDR, PLLs, MIO), hands the PM configuration object to the
   PMU firmware and loads `u-boot-<hash>.itb` from the same partition: TF-A
   `bl31` to OCM (`0xfffea000`), U-Boot to `0x8000000`. The file is named
   after its build (16 hex digits of the U-Boot recipe's `do_compile` task
   hash, `CONFIG_SPL_FS_LOAD_PAYLOAD_NAME`), so each `boot.bin` loads only the
   `u-boot.itb` it was built with (see
   [Updating with SWUpdate](#updating-with-swupdate)).
3. TF-A starts U-Boot in EL2, which runs the compiled-in eicke bootcmd
   (`recipes-bsp/u-boot/files/te0820/eicke-te0820.cfg`).

The A/B contract is the same as on [ax7015b](ax7015b.md#boot-flow-and-ab): the
state is in `uboot.env` on `mmc 1:1` (U-Boot numbering), guarded by an env whitelist
(`0001-zynqmp-eicke-env-flags-whitelist.patch`), and the bootcmd loads the active
slot's `/boot/Image` and `/boot/zynqmp-te0820.dtb` and boots with
`root=PARTUUID=<slot partition>` and `eicke.slot=<slot>`. The card has the same
MBR layout (`eicke-ab-zynq-sd.wks.in`).

## Build

```sh
MACHINE=te0820 bitbake eicke-image-dev         # microSD wic (+ .wic.bmap)
MACHINE=te0820 bitbake eicke-update-image-dev  # its .swu
MACHINE=te0820 bitbake eicke-update-bootloader # boot.bin + u-boot.itb .swu
```

The machine needs meta-arm (`meta-arm/meta-arm` and `meta-arm/meta-arm-toolchain`
in `bblayers.conf`, from the manifest) for TF-A.

## Flash and boot

```sh
DEPLOY=build-integration/tmp/deploy/images/te0820
bmaptool copy $DEPLOY/eicke-image-dev-te0820.rootfs.wic $DEV   # e.g. /dev/sdX on the host
```

1. Put the card in the TE0703's microSD slot.
2. Select **SD boot** with DIP switch **S2** on the TE0703 (tested on REV05):

   | S2-1 | S2-2 | S2-3 | S2-4 |
   |---|---|---|---|
   | OFF | ON | ON | ON |

   S2-4 is MIO0 (ON = SD, OFF = QSPI); S2-1 is PGOOD on current CPLD
   firmware (S2-1 and S2-4 both ON is JTAG boot). S2-2/S2-3 ON route the
   FTDI's JTAG to the Zynq. With SD selected, the RJ45 LEDs are orange
   (green: QSPI).
3. Attach the **console** on the TE0703's mini-USB **J4** (FTDI FT2232H,
   shown as "Digilent USB Device"; the second of its two serial ports,
   e.g. `/dev/ttyUSB1`), 115200 8N1. The carrier's CPLD routes it to the
   module's UART0 (MIO 30/31). The FTDI is powered by the board, so the port
   disappears while the board is off; use the reset button to reboot
   without losing it. Some mini-USB cables fail to enumerate it
   (`Cannot enable. Maybe the USB cable is bad?`).
4. Power the carrier with 5 V on J13.

SPL prints `U-Boot SPL ...`, then TF-A `NOTICE:  BL31: ...`, then U-Boot should
print `Loading Environment from FAT... OK` and
`Eicke Linux (rootfs_a): booting /boot/Image`. Then, on the target:

```sh
cat /proc/cmdline                     # eicke.slot=rootfs_a
fw_printenv rootdev ustate bootcount  # rootfs_a 0 0
ls -l /dev/eicke/                     # esp rootfs_a rootfs_b data -> mmcblk0p1..4
ip link show end0                     # the MAC from the EEPROM
```

Log in as `root` with an empty password (the dev image's `EXTRA_IMAGE_FEATURES`).

### JTAG

The first FTDI channel is a Digilent-compatible JTAG cable, so Vivado/Vitis
`hw_server`/`xsdb` work without a separate probe (S2-2 and S2-3 ON). The
user needs write access to the USB device, e.g. a udev rule
`SUBSYSTEM=="usb", ATTR{idVendor}=="0403", ATTR{idProduct}=="6010", MODE="0666"`.
To run a new SPL without writing the card: set the alternate boot mode to
JTAG (`mwr 0xff5e0200 0x0100`), `rst -system`, enable the PMU
(`mwr 0xffca0038 0x1ff`), `dow pmufw.elf` + `con` on the MicroBlaze PMU, set
the alternate boot mode back to SD1 (`mwr 0xff5e0200 0x5105`), then on
Cortex-A53 #0 `rst -processor`, `dow -data spl/u-boot-spl.bin 0xfffc0000`,
`rwr pc 0xfffc0000`, `con`. SPL then loads its `u-boot-<hash>.itb` from the
card (copy the build's `deploy/images/te0820/eicke-esp/u-boot-*.itb` there).

**Do not attach the debugger to a running Linux.** `hw_server` arms a reset
catch on the A53s that outlives the session: the next time cpuidle powers a
core down and it wakes up through reset, it halts. Its interrupts stay
pending, and the system degrades (microSD command timeouts and `card
removed`, services hitting their watchdogs) until a reset. `xsdb` then shows
`Cortex-A53 #0 (Reset Catch)`; `con` on that core gets the system going
again, a reset clears it for good.

## Watchdog

A trial boot that hangs is reset and rolled back. U-Boot starts the FPD
system watchdog (`watchdog0`, `cdns-wdt`, 60 s; `CONFIG_WDT_CDNS`,
`WATCHDOG_AUTOSTART`) and leaves it running: it does not feed it itself (no
`CONFIG_CYCLIC`), so a boot stuck at the U-Boot prompt is reset too (`wdt
stop` to work there), and the kernel's driver leaves it alone until systemd
opens it and feeds it (`eicke-watchdog`, `RuntimeWatchdogSec=30s`). When it
expires, the PMU firmware's error manager resets the whole system, and
U-Boot's bootcmd finds `ustate=1`, `bootcount=1` and switches back to the
other slot (`ustate=3`). `panic=10` on the kernel command line reboots a
trial slot that panics (e.g. cannot mount its rootfs) sooner.

The machine conf, not the image, pulls in `eicke-watchdog`
(`MACHINE_ESSENTIAL_EXTRA_RRECOMMENDS`, through `packagegroup-core-boot`):
U-Boot starts the watchdog for every image, so an image without the feeder
(e.g. `core-image-minimal`) would be reset 60 s after U-Boot, over and over.
An image that is not based on `packagegroup-core-boot`, or does not run
systemd, needs another feeder.

The SWDT's own reset output resets only the APU, which then lands in TF-A
without U-Boot, so the system reset has to come from the PMU: its error
manager (`ENABLE_EM`) routes the LPD/FPD SWDT errors to a system reset once
the first stage boot loader reports completion in `GEN_STORAGE5`, which the
Xilinx FSBL does and our SPL does too
(`0002-arm64-zynqmp-spl-signal-boot-loader-completion-to-PMU.patch`).
`GEN_STORAGE5` reads `0xb` after boot (bit 3: the PMU firmware took it) and
`ERROR_SRST_MASK_1` has bits 12/13 clear.

Tested on the board, each time with a trial slot that does not confirm:
`kernel.panic=0` and `echo c > /proc/sysrq-trigger` (systemd stops feeding):
reset 34 s later, previous slot booted; `/sbin/init` replaced by a script
that sleeps (systemd never starts, only U-Boot's watchdog runs): reset 60 s
after U-Boot started it, previous slot booted. (`kill -STOP 1` is no test:
the kernel does not stop PID 1.)

## Updating with SWUpdate

The board runs `swupdate` with its web server on port 8080 (allowed by the
image's firewall). From the build host:

```sh
curl -F filename=@$DEPLOY/eicke-update-image-dev-te0820.rootfs.swu http://<board>:8080/upload
ssh root@<board> reboot
```

The bundle (the rootfs, with its own `/boot/Image` and DTB) is streamed
into the standby slot, `rootdev` points at it with `ustate=1`, and U-Boot
boots it as a trial; `eicke-bootconfirm` confirms it (`ustate=0`). Tested
on the board in both directions (`rootfs_a` -> `rootfs_b` -> `rootfs_a`),
about 40 s for the 620 MB bundle. The DHCP client identifies itself by MAC,
so the board keeps its address across slots.

The bootloader is not part of the rootfs bundle: it exists only once (no A/B
for `boot.bin`), so it has a bundle of its own, `eicke-update-bootloader`
(`MACHINE=te0820 bitbake eicke-update-bootloader`), installed the same way:

```sh
curl -F filename=@$DEPLOY/eicke-update-bootloader-te0820.rootfs.swu http://<board>:8080/upload
```

It writes `boot.bin` and `u-boot.itb` to the ESP as `*.new`; its script
(`eicke-bootloader-swap.sh`) then switches with a single rename:

1. It renames `u-boot.itb.new` to the name the new SPL loads, read from
   `boot.bin.new` (`u-boot-<hash>.itb`). The current `boot.bin` loads a
   different file, so it still boots its own pair.
2. It copies the current `boot.bin` to `BOOT0001.BIN`.
3. It renames `boot.bin.new` to `boot.bin`: from here on the new pair boots.
   On FAT this is one directory entry update, so after a power loss
   `boot.bin` is either the old or the new file, each with its own `.itb`.
4. It deletes the `.itb` files neither `boot.bin` nor `BOOT0001.BIN` loads.

`BOOT0001.BIN` is the boot ROM's fallback: if `boot.bin` is missing or its
boot header is invalid (a torn write), the golden image search (UG1085)
boots `BOOT0001.BIN`, the previous bootloader, with its `.itb`. Not yet
tested on the board (corrupt `boot.bin`'s header to test it). A `boot.bin`
that is valid but hangs is not caught. It leaves `ustate` alone
(`bootloader_state_marker = false`; by default SWUpdate sets `ustate=1`
after an install, which the bootcmd would take for a trial of the running
slot). The new bootloader runs from the next boot on, without a trial: if
it does not boot, copy `BOOT0001.BIN` to `boot.bin` on another machine (or
reflash). A card with the bootloader from before the per-build names
(`u-boot.itb`) updates the same way: its `boot.bin` and `u-boot.itb` become
the fallback. Tested on the board (the U-Boot with the watchdog came this
way).

Rollback was tested on the board too: an update whose slot does not confirm
(its `eicke-bootconfirm.service` masked) is booted once (`bootcount=1`); the
next boot goes back to the previous slot with `ustate=3`.

## R5 firmware (RustAmp)

Both Cortex-R5Fs run in split mode, each with RustAmp's `zynqmp-r5-echo`
(`recipes-bsp/rustamp-r5-echo`), loaded by Linux's `xlnx_r5_remoteproc`:

| | R5_0 | R5_1 |
|---|---|---|
| remoteproc | `remoteproc0` (`ffe00000.r5f`) | `remoteproc1` (`ffe90000.r5f`) |
| firmware | `/lib/firmware/rustamp-r5_0-echo.elf` | `/lib/firmware/rustamp-r5_1-echo.elf` |
| IPI channel (APU: 0) | 1, mailbox `ff990400` | 2, mailbox `ff990440` |
| resource table, trace | `0x3ed00000` (`rproc_0_fw_image`) | `0x3ef00000` (`rproc_1_fw_image`) |
| vrings, buffers | `0x3ed40000`, 1 MiB pool | `0x3ef40000`, 512 KiB pool |

The recipe builds the example twice (cargo feature `r5-1` for R5_1) with
the prebuilt Rust toolchain's `armv7r-none-eabihf` and the example's
crates.io dependencies vendored through `crate://`. Its patches (to be
upstreamed to RustAmp) add `no-uart` (UART1 is not routed: the firmware
logs only to the remoteproc trace buffer), `r5-1`, and a reset handler that
starts every core as core 0 (aarch32-rt's default parks any core whose
MPIDR affinity is not 0, which R5_1's is).

```sh
echo rustamp-r5_1-echo.elf > /sys/class/remoteproc/remoteproc1/firmware
echo start > /sys/class/remoteproc/remoteproc1/state
cat /sys/kernel/debug/remoteproc/remoteproc1/trace0
ptest-runner rustamp-r5-echo   # both cores: echo, 2 reloads
cd /usr/lib/rustamp-r5-echo/ptest && ./rpmsg_bench.py   # latency, throughput
```

The ptest starts both cores, runs 2000 checked echo round trips on both
`/dev/ttyRPMSG*` at once (a core's tty is found through sysfs, since the
numbering follows the start order) and reloads both twice.
`rpmsg_bench.py`, installed next to it but run by hand (it takes about a
minute and adds no pass/fail coverage), measures round-trip latency and
throughput on running cores, and fails if an echo is broken or the bytes
echoed differ from those sent. Measured on
the board (Python through `rpmsg_tty`, so this includes the tty layer and
the interpreter; both concurrent streams share one interpreter):

| | latency median (1/64/256 B) | p99 | throughput (echoed) |
|---|---|---|---|
| one core alone | 146 / 146 / 152 us | 170-245 us | 1.6-2.1 MB/s |
| both at once, per core | 250-270 us | 470-550 us | ~1.0 MB/s |

`failed to get rpu node status, err -95` at boot is a warning: the driver
asks the PMU firmware whether the R5 already runs (to attach to it), which
needs an EEMI call this firmware does not offer.
