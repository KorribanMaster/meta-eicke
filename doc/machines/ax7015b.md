# ax7015b

**ALINX AX7015B**: the AC7015B core board (Xilinx Zynq-7000 XC7Z015, 2× Cortex-A9
at 767 MHz, 1 GiB DDR3, 8 GB eMMC, 32 MiB QSPI flash) on the AX7015B carrier. The
board runs the eicke A/B image from a **microSD card**. Only the processing system
(PS) is used: the programmable logic (PL) is not loaded at boot. Linux runs on
CPU0; **CPU1 runs the [RustAmp](https://github.com/KorribanMaster/rustamp) rpmsg
echo firmware**, loaded and started through `remoteproc` (AMP).

The same board served as the PCIe "RTU" of the x86 machines
([zynq-pcie-rproc](../../recipes-kernel/zynq-pcie-rproc), bare-metal firmware loaded
by the host). This machine is the other way round: Linux runs on the Zynq itself.

## Where the BSP comes from

No meta-xilinx and no Xilinx tools in the build: everything comes from oe-core and
the board files in meta-eicke.

| Piece | Source |
|---|---|
| Machine conf | `conf/machine/ax7015b.conf` |
| Boot ROM payload (replaces the Xilinx FSBL) | U-Boot SPL `boot.bin`, `xilinx_zynq_virt_defconfig` + `recipes-bsp/u-boot/files/ax7015b/` |
| DDR, clocks, MIO | `ps7_init_gpl.c/h` from the Vivado reference design, built into SPL |
| U-Boot | oe-core `u-boot` 2026.01, `u-boot.img` (FIT) |
| Kernel | `linux-yocto` 6.18, kernel-cache BSP `amd-zynq` (`KMACHINE`) + `ax7015b.cfg` |
| Device tree | `files/dts/zynq-ax7015b.dts`, one file for U-Boot and Linux |
| CPU1 firmware | `rustamp-a9-echo` (RustAmp `examples/cortex-a9-rtu-echo`, prebuilt `rust-bin-thumbv7em-native` toolchain) |
| CPU1 remoteproc driver | `a9-rproc` (RustAmp `linux/a9-rproc`, out-of-tree module) |

`ps7_init_gpl.c/h` come from the ALINX reference design
`AX7015B_2023.1/course_s4_linux/01~07_ax_peta` (`design_1_wrapper.xsa`, identical to
the PetaLinux BSP's `hw-description`). They are GPL and generated by Vivado for this
use. After a change of the PS configuration in Vivado, export the XSA again and
copy the two files out of it (the XSA is a zip).

### Hardware described

From the reference design's `ps_config.tcl` and the ALINX user manual:

| MIO | Function | Device tree |
|---|---|---|
| 1–6 | QSPI flash (W25Q256) | `&qspi`, `jedec,spi-nor` |
| 7 | Ethernet PHY reset (active low) | `reset-gpios` of `ethernet-phy@1` |
| 8 | USB3320C reset (active low) | GPIO hog, released at GPIO probe |
| 10 | microSD card detect | SD0 controller |
| 12–13 | UART1, console (CP2102 on the carrier) | `&uart1`, `ttyPS0` |
| 16–27, 52–53 | GEM0 RGMII + MDIO | `&gem0`, PHY at address 1 |
| 28–39 | USB0 ULPI, host via a USB2514 hub | `&usb0` |
| 40–45 | SD0, microSD (boot, A/B disk) | `&sdhci0`, `mmc0` |
| 46–51 | SD1, eMMC (4 bit) | `&sdhci1`, `mmc1` |

The PS Ethernet PHY is a JL2121 on current boards (a KSZ9031 on older ones). Linux
has no JL2121 driver and uses the generic PHY driver; the RGMII delays are strapped
in the PHY.

The USB3320C reset is a GPIO hog, not `reset-gpios` of the `usb-nop-xceiv`: as
the latter it is only released in the controller's PHY init, right before
ChipIdea's own reset, while the ULPI clock is not running yet, and `ci_hdrc` then
fails silently at boot.

Not available without a bitstream: the second Ethernet port (PL, AXI Ethernet),
HDMI in/out, the PL LEDs and keys, and I2C0/1 (routed through EMIO).

## Boot flow and A/B

1. The boot ROM (DIP switch on SD) loads `boot.bin` from the first FAT partition of
   the microSD. This is U-Boot SPL with the Zynq boot header.
2. SPL runs `ps7_init` (DDR, PLLs, MIO) and loads `u-boot.img` from the same
   partition.
3. U-Boot runs the compiled-in eicke bootcmd
   (`recipes-bsp/u-boot/files/ax7015b/eicke-ax7015b.cfg`).

The A/B contract is the same as on [qemuarm-uboot](qemuarm-uboot.md) and
[ccimx8mn-dvk](ccimx8mn-dvk.md#ab-boot):

- The A/B state (`rootdev`/`ustate`/`bootcount`) lives in **`uboot.env` on the
  microSD's FAT partition** (`mmc 0:1`). Userspace reaches it via
  `fw_printenv`/`fw_setenv` and SWUpdate's U-Boot handler (the `eicke-ubootenv`
  override).
- An **env whitelist** (`CONFIG_ENV_WRITEABLE_LIST` + `CFG_ENV_FLAGS_LIST_STATIC` in
  `0001-zynq-eicke-env-flags-whitelist.patch`) keeps `uboot.env` from overriding
  anything but the A/B variables and the variables the Zynq board code sets at boot.
- The bootcmd loads the **active slot's** `/boot/zImage` and
  `/boot/zynq-ax7015b.dtb` and boots with `root=PARTUUID=<slot partition>` and
  `eicke.slot=<slot>`.

### MBR, not GPT

The Zynq-7000 boot ROM only finds `boot.bin` on an **MBR** disk; it does not read
GPT. The card therefore has an msdos partition table, and the partitions have no
names. `eicke-bootpart` (and with it `/dev/eicke/*`, the fstab and the SWUpdate
hook) maps the slots by partition number on a disk whose partitions have no names
at all: p1 `esp`, p2 `rootfs_a`, p3 `rootfs_b`, p4 `data`. GPT disks are never
matched by number. MBR PARTUUIDs (`<disk id>-02`) work for U-Boot's `part uuid` and
the kernel's `root=PARTUUID=`.

## Build

```sh
MACHINE=ax7015b bitbake eicke-image-dev         # microSD wic (+ .wic.bmap)
MACHINE=ax7015b bitbake eicke-update-image-dev  # its .swu
```

Card layout (`files/wic/eicke-ab-zynq-sd.wks.in`, MBR):

| Partition | What |
|---|---|
| p1 `esp` (FAT, 64 MiB) | `boot.bin`, `u-boot.img`, `uboot.env` |
| p2 `rootfs_a`, p3 `rootfs_b` | 1 GiB each |
| p4 `data` | 4 GiB |

## Flash and boot

```sh
DEPLOY=build-integration/tmp/deploy/images/ax7015b
bmaptool copy $DEPLOY/eicke-image-dev-ax7015b.rootfs.wic $DEV   # e.g. /dev/sdX on the host
```

1. Put the card in the carrier's microSD slot.
2. Set **SW1** on the core board to **OFF, OFF** (SD card). ON, ON is JTAG and
   OFF, ON is QSPI.
3. Attach the **console** on the carrier's USB-UART (CP2102, UART1 = `ttyPS0`,
   115200 8N1). A worn mini-USB cable shows up as `cp210x ... status: -71` in the
   host's kernel log: the adapter enumerates but cannot be opened. If the login
   prompt turns to garbage after line noise, agetty has dropped to a lower rate
   (`--keep-baud`); 57600 then works until the next boot.

SPL prints `U-Boot SPL ...` and loads `u-boot.img`; U-Boot should print
`Loading Environment from FAT... OK` and
`Eicke Linux (rootfs_a): booting /boot/zImage`. Then, on the target:

```sh
cat /proc/cmdline                     # eicke.slot=rootfs_a
fw_printenv rootdev ustate bootcount  # rootfs_a 0 0
ls -l /dev/eicke/                     # esp rootfs_a rootfs_b data -> mmcblk0p1..4
```

Log in as `root` with an empty password (the dev image's `EXTRA_IMAGE_FEATURES`).

## Test CPU1 (AMP)

```sh
ptest-runner rustamp-a9-echo        # in eicke-image-dev
```

It starts `rustamp-a9-echo.elf` on CPU1 through
`/sys/class/remoteproc/remoteproc0` (`remoteproc-cpu1`), waits for
`/dev/ttyRPMSG0`, and checks 2000 echo round trips. Then it stops and restarts the
firmware twice and repeats the round trips after each restart. Manually:

```sh
echo start > /sys/class/remoteproc/remoteproc0/state
stty -F /dev/ttyRPMSG0 raw -echo
cat /dev/ttyRPMSG0 & echo hello > /dev/ttyRPMSG0   # prints "hello"
echo stop > /sys/class/remoteproc/remoteproc0/state  # CPU1 parks; start reloads
```

Verified on the board: `PASS: 3 runs of 2000 round trips` (about 5 s).

How it fits together:

- **Linux runs on CPU0 only.** `maxcpus=1` comes from the kernel config
  (`CONFIG_CMDLINE` + `CMDLINE_EXTEND` in `ax7015b.cfg`), so it is part of each
  slot's kernel and arrives with an update. U-Boot's bootcmd is not updated by
  SWUpdate.
- **CPU1 waits in the boot ROM's loop** for an entry address at `0xfffffff0` in
  OCM. U-Boot SPL (in place of the FSBL) keeps its stack below `0xfffffe00`, so the
  loop survives. On the first start, `a9-rproc` writes the entry there and wakes
  CPU1 with `sev`. On later starts, it releases CPU1 from the firmware's park page.
- **The top 32 MiB of DDR are CPU1's** (`0x3E000000`–`0x3FFFFFFF`, `no-map`): the
  firmware image, resource table and park page, the vrings and the rpmsg buffer pool.
  It's the same layout as RustAmp's ZC702 QEMU example.
- **Notifications are SGIs:** 15 to CPU1, 14 to Linux.
- **The firmware has no debug output.** Its UART0 is neither routed to MIO on this
  board nor clocked by `ps7_init`, and touching a gated peripheral stalls the bus.
  The recipe builds it with the `no-uart` feature (RustAmp patch). For a CPU1 log,
  enable UART0 in the Vivado design (MIO or EMIO to a PL header), or read CPU1's
  state over JTAG (`xsdb`, `targets` / `rrd`).
- **`a9-rproc` must be signed** like every module (the kernel has
  `MODULE_SIG_FORCE`). kbuild signs it in `modules_install`, a target RustAmp's
  `Makefile` gets from the recipe's patch.

The PS Ethernet port is the RJ45 jack labelled **ETH1** on the carrier (the other
one belongs to the PL). It gets its address by DHCP.

## A/B update

```sh
scp -O $DEPLOY/eicke-update-image-ax7015b.rootfs.swu root@<board>:/data/update.swu
ssh root@<board> swupdate -i /data/update.swu   # writes the standby slot, ustate=1
ssh root@<board> reboot                         # boots the new slot, bootconfirm -> ustate=0
```

Tested on the board in both directions (A → B, B → A). Rollback: a trial boot
that is reset before `eicke-bootconfirm` runs (`ustate=1`, `bootcount=1`) is
followed by a boot of the previous slot with `ustate=3`.

A slot whose kernel never starts or that hangs without a reset is not rolled back
automatically: no watchdog is enabled yet, so the board needs a power cycle.

## Not done yet

- **eMMC + QSPI boot.** SPL and U-Boot in the QSPI flash, the A/B disk on the eMMC,
  no microSD needed. Needs a QSPI flashing step and an install flow onto the eMMC.
- **PL.** Loading a bitstream (from U-Boot, or from Linux through the FPGA manager)
  and describing its peripherals.
- **MAC address.** The board has no MAC storage. U-Boot makes up a random MAC on
  every boot and hands it to Linux in the device tree, where it counts as
  permanent, so the address (and with it the DHCP lease) changes on each boot.
- **QSPI flash in Linux.** The mainline `spi-zynq-qspi` driver supports at most
  3 address bytes, and spi-nor uses 4-byte addressing for the 32 MiB W25Q256:
  `spi-nor spi0.0: probe with driver spi-nor failed with error -22`. Needs a
  driver change before the QSPI boot step.
- **Watchdog.** The Zynq's `cdns,wdt-r1p2` (or the SWDT) is not enabled, so a
  hung trial boot is not reset into the rollback.
- **SMP Linux.** With CPU1 given to the firmware, Linux has one core. A machine
  variant without the AMP pieces (no `maxcpus=1`, no `remoteproc-cpu1`) would give
  Linux both cores back.
- **Prod image.** `eicke-image-prod` (signed kernel FIT, read-only rootfs) is not
  enabled for this machine.
